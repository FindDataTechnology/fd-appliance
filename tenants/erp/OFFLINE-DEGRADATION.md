# ERP 机房版：断网时什么照常、什么不可用

> 判据来自实测，不是设计推演：
> - **真机镜像** `platform:sha-92a2ae1` 在 k3s 上以 `AUTH_MODE` 未设、无 `CLOUD_MODE`
>   起单进程，`NetworkPolicy` 全拒 Egress 后冷启动
> - **交付栈**在 GitHub runner 上以 `docker network create --internal` 起栈，
>   并反证容器内出网被拒
>
> 两份证据在 `openspec/changes/erp-appliance-carries-platform/tasks.md` 的 1.3 / 3.2。

## 一句话

**断网时：登录、读账、看团队运行态照常；对话与团队「干活」不可用。**
这个降级是**如实呈现**的——LLM 面报「没有可用模型」，不是转圈、不是空答案、不是零值冒充。

## 逐项

| 面 | 断网时 | 实测依据 |
|---|---|---|
| 登录 / 产品面四路由 | **照常** | `/chat` `/agents` `/dashboard` `/knowledge` 全 200 |
| 账务数据读取 | **照常** | 内核 32 个工具面对公网零依赖；数据在客户机房的 PG 里 |
| 团队列表 / 驾驶舱 / 运行历史 | **照常** | `/api/fleets/overview`、`/api/fleets/:id`、`/courier`、`/cockpit` 全 200 |
| 文件 / 资源 / 文档 | **照常** | `/api/resources`、`/api/documents` 全 200 |
| 汇率折算 | **用随包基线** | `erp-fx-baseline` 是 `ship_with` 档，近 12 月切片在包里；日更走 `online_increment`，断网不更新 |
| **LLM 推理 / 对话** | **不可用** | WS `list_models` 返 `models:[]`（如实为空，不是报错也不是假装有） |
| **团队执行（agent 干活）** | **不可用** | 团队要跑起来需要 `agent-runner` + 可达的 LLM；`external-llm-gateway` 是 `cloud_locked` |
| 团队**运行态查看** | **照常** | 与「团队执行」是两件事：能看历史，不能产生新的回合 |

## 售前/交付时必须说清的三句话

1. **看得到，干不了。** 断网时客户能登录、能查账、能看团队的历史运行态与已有的报数，
   但**不能让团队再跑一轮**——那一轮要调模型。
2. **不是「功能阉割」，是「依赖如实」。** LLM 在交付包的 `components.json` 里登记为
   `cloud_locked`，`degrades_to` 字段就写着「断网时对话与团队运行不可用，数据面与账务读取照常」。
3. **客户可以自带内网 LLM 网关**（`external-llm-gateway` 的 `substitute` 一栏）：
   装后配 BYOK，凭证经环境变量注入、零落库零日志、不入包。配好之后对话与团队执行恢复可用，
   但那时它就不再是「断网」形态了——是「不出公网」。

## 不要做的事

- **不要把「团队执行不可用」写成「团队不可用」。** 团队仍然存在于产品面里，成员、编制、
  历史报数、待拍板项都看得到；只是新回合跑不起来。这两件事在客户那里的感受完全不同。
- **不要用空数据或零值冒充不可用的面。** 断网时 `/api/resources` 返回 `items: []` 是因为
  真的没有资源，不是「读不到所以装作空」——如果哪天变成了后者，那是个 bug 而不是降级。
- **不要把这份文档当成「断网也能全功能」。** 第 2 节列的三步部署动作（每租户一份
  `fd-erp-vertical-api` 等）与断网无关，别混在一起说。
